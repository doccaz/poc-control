HPA em um nginx no k3s, com acesso por Ingress (<HOST_APLICACAO>)

Objetivo: criar um nginx simples pela UI do Rancher (Deployment com Service NodePort), escalar com um HPA sob carga, e acessá-lo por Ingress com o nome <HOST_APLICACAO>.

Fluxo: 1 Pré-requisitos → 2 Deployment e Service (UI) → 3 HPA → 4 Carga e observação → 5 Ingress (bônus).

Convenções: arquivos são criados no editor (vi), e os comandos do k3s rodam no nó como root. Onde aparece <...>, troque pelo valor real.

Valores desta sessão

Item Valor
IP do nó do k3s <IP_NODE_K3S>
Namespace hpa-teste (sugestão)
Nome do Deployment nginx-hpa (sugestão)
Imagem <REGISTRY_QUAY>/nginx:latest (a do Quay, já validada), ou nginx:latest
Nome para o Ingress <HOST_APLICACAO>

O que ressaltar

Ponto Por que importa Como tratar
requests de CPU O HPA calcula a utilização como uso dividido pelo request. Sem ele, o alvo fica <unknown> e nada escala Preencher a reserva de CPU no passo 2
Metrics Server O HPA lê as métricas dele Conferir no passo 1
Porta da imagem O nginx oficial escuta na 80; a variante unprivileged escuta na 8080 Confirmar a porta da imagem do Quay
Escalonamento para baixo é lento O padrão espera cerca de 5 minutos antes de reduzir Esperado. O HPA do passo 3 encurta para 1 minuto, só para a demonstração
DNS do nome O nome <HOST_APLICACAO> precisa de um registro apontando para o nó Pedir ao admin de DNS. Enquanto isso, testar com o cabeçalho Host
Controlador de Ingress Sem ele, o objeto Ingress existe mas ninguém o atende Conferir no passo 1

1. Pré-requisitos — no nó do k3s

Métricas:

kubectl get apiservice v1beta1.metrics.k8s.io
kubectl top nodes

Esperado: o apiservice com AVAILABLE igual a True, e o top nodes mostrando CPU e memória do nó. Se o top der erro, o metrics-server não está disponível, e o HPA não funcionará.

Controlador de Ingress (para o passo 5):

kubectl get ingressclass
kubectl -n kube-system get svc | grep -i traefik

Esperado: uma IngressClass traefik e um Service traefik do tipo LoadBalancer, com EXTERNAL-IP igual ao IP do nó e as portas 80 e 443. Se não houver nenhuma IngressClass, o cluster não tem controlador de Ingress, e o passo 5 precisa de um (veja a última tabela).

2. Deployment e Service — pela UI do Rancher

☰ → o seu cluster → Workloads → Deployments → Create. Preencha (os nomes dos campos variam um pouco entre versões do Rancher):

Campo Valor
Namespace Crie um novo: hpa-teste
Name nginx-hpa
Replicas 1
Container Image A imagem da tabela de valores
Ports (Add Port or Service) Service Type NodePort, Private Container Port 80, nome http
CPU Reservation 50 mCPU (é o requests.cpu)
Memory Reservation 64 MiB
CPU Limit 200 mCPU
Memory Limit 128 MiB

O ponto crítico é a reserva de CPU: ela vira o request, que o HPA usa como base. Clique em Create.

Conferir:

kubectl get deploy,pods,svc -n hpa-teste
kubectl get deploy nginx-hpa -n hpa-teste -o jsonpath='{.spec.template.spec.containers[0].resources}'; echo

Esperado: o pod Running, um Service NodePort com uma porta do tipo 80:3xxxx/TCP, e os resources mostrando requests com cpu: 50m. Anote o nome do Service e a porta 3xxxx (o NodePort), que os próximos passos usam.

Teste o acesso direto, trocando <NODEPORT>:

curl -s -o /dev/null -w "HTTP %{http_code}\n" http://127.0.0.1:<NODEPORT>/

Esperado: HTTP 200.

Se preferir criar pelo editor: abra vi /tmp/nginx-hpa.yaml, cole o conteúdo abaixo, salve e rode kubectl apply -f /tmp/nginx-hpa.yaml. Ele equivale ao que o formulário cria:

apiVersion: v1
kind: Namespace
metadata:
  name: hpa-teste
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-hpa
  namespace: hpa-teste
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-hpa
  template:
    metadata:
      labels:
        app: nginx-hpa
    spec:
      containers:
      - name: nginx
        image: <REGISTRY_QUAY>/nginx:latest
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 200m
            memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: nginx-hpa
  namespace: hpa-teste
spec:
  type: NodePort
  selector:
    app: nginx-hpa
  ports:
  - name: http
    port: 80
    targetPort: 80

3. HPA

Abra o arquivo:

vi /tmp/hpa.yaml

Cole este conteúdo e salve:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
  namespace: hpa-teste
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-hpa
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60

O que cada parte faz:

Campo Efeito
scaleTargetRef O Deployment que será escalado. O nome precisa ser igual ao do Deployment
minReplicas e maxReplicas De 1 a 5 réplicas. O máximo precisa caber no nó (5 × 50m de CPU)
averageUtilization: 50 Escala quando o uso médio passa de 50% do request (ou seja, de 25m por pod)
behavior.scaleDown Reduz a espera de 5 minutos para 1, só para a demonstração. Em produção, mantenha o padrão

Aplique e confira:

kubectl apply -f /tmp/hpa.yaml
kubectl get hpa -n hpa-teste

Esperado: nos primeiros 15 a 30 segundos o alvo aparece como <unknown>/50%. Depois, algo como 1%/50%, com REPLICAS igual a 1.

Se o alvo continuar <unknown>, veja o motivo:

kubectl describe hpa nginx-hpa -n hpa-teste

(As causas estão na tabela do final.) Pela UI do Rancher, o HPA também aparece em Workloads → HorizontalPodAutoscalers.

4. Carga e observação

Abra dois terminais no nó. No primeiro, acompanhe:

kubectl get hpa -n hpa-teste -w

No segundo, gere carga. O comando inicia 20 loops em paralelo e cada um para sozinho depois de 240 segundos. Troque <NODEPORT>:

for i in $(seq 1 20); do timeout 240 sh -c 'while true; do curl -s -o /dev/null http://127.0.0.1:<NODEPORT>/; done' & done

Num terceiro terminal (ou depois), veja os pods e o uso:

kubectl get pods -n hpa-teste
kubectl top pods -n hpa-teste

Esperado:

  1. O alvo sobe acima de 50% em cerca de 30 a 60 segundos.
  2. As REPLICAS aumentam (2, 3, até no máximo 5).
  3. Passados os 240 segundos, a carga para, o alvo cai, e depois de cerca de 1 minuto as réplicas voltam a 1.

Evidência: os eventos do HPA mostram cada decisão, com o motivo:

kubectl describe hpa nginx-hpa -n hpa-teste

Procure linhas SuccessfulRescale com a mensagem "above target" (subida) e "All metrics below target" (descida).

Se o HPA não escalar, o nginx pode estar servindo tão rápido que o uso não passa de 25m por pod. Aumente os loops (troque 20 por 50) ou reduza a reserva de CPU para 20 mCPU, e reaplique.

5. Ingress — bônus, <HOST_APLICACAO>

5.1 O que você precisa

Requisito O que fazer
Controlador de Ingress Passo 1: IngressClass traefik
Registro DNS O admin de DNS cria <HOST_APLICACAO> (tipo A) apontando para <IP_NODE_K3S>. O Traefik escuta nas portas 80 e 443 do nó
Firewall Liberar os clientes (navegadores) até <IP_NODE_K3S>, portas 80 e 443
Certificado, para HTTPS Opcional (5.4). Sem ele, o Traefik usa um certificado próprio e o navegador avisa

5.2 Criar o Ingress

Confirme o nome do Service e a porta dele (a primeira, antes dos :):

kubectl get svc -n hpa-teste

Abra o arquivo:

vi /tmp/ingress.yaml

Cole este conteúdo e salve (troque o nome do Service e a porta, se forem diferentes):

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-hpa
  namespace: hpa-teste
spec:
  ingressClassName: traefik
  rules:
  - host: <HOST_APLICACAO>
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: nginx-hpa
            port:
              number: 80

kubectl apply -f /tmp/ingress.yaml
kubectl get ingress -n hpa-teste

Esperado: o Ingress listado com o HOST <HOST_APLICACAO> e o ADDRESS igual ao IP do nó.

5.3 Testar

Antes do DNS existir, envie o nome no cabeçalho Host, no próprio nó:

curl -i -H "Host: <HOST_APLICACAO>" http://<IP_NODE_K3S>/

Esperado: HTTP/1.1 200 OK e o HTML "Welcome to nginx!".

Para abrir no navegador sem DNS, acrescente uma linha ao arquivo hosts da sua máquina (no Windows, C:\Windows\System32\drivers\etc\hosts, aberto como administrador): <IP_NODE_K3S> <HOST_APLICACAO>. Depois, acesse http://<HOST_APLICACAO>/.

Depois do DNS:

nslookup <HOST_APLICACAO>
curl -i http://<HOST_APLICACAO>/

Esperado: o nslookup devolve <IP_NODE_K3S>, e o curl, HTTP/1.1 200 OK.

Carga pelo Ingress (opcional, no lugar do NodePort do passo 4): use o mesmo comando de carga, trocando a URL por http://<IP_NODE_K3S>/ e acrescentando -H "Host: <HOST_APLICACAO>" ao curl. Assim o HPA é provado também pelo caminho do Ingress.

5.4 HTTPS (opcional)

Você precisa do certificado e da chave para <HOST_APLICACAO> (o nome precisa constar no certificado). Crie o Secret no editor:

umask 077
vi /tmp/tls-secret.yaml

Cole este conteúdo, cole o certificado e a chave (em PEM) nos campos indicados, e salve:

apiVersion: v1
kind: Secret
metadata:
  name: aplicacao-tls
  namespace: hpa-teste
type: kubernetes.io/tls
stringData:
  tls.crt: |
    <CERTIFICADO_PEM_COM_A_CADEIA>
  tls.key: |
    <CHAVE_PRIVADA_PEM>

kubectl apply -f /tmp/tls-secret.yaml
rm -f /tmp/tls-secret.yaml

Depois, abra o Ingress (vi /tmp/ingress.yaml), acrescente o bloco tls ao spec, no mesmo nível de rules, e reaplique:

  tls:
  - hosts:
    - <HOST_APLICACAO>
    secretName: aplicacao-tls

kubectl apply -f /tmp/ingress.yaml
curl -i https://<HOST_APLICACAO>/

Esperado: HTTP/1.1 200 OK, sem aviso de certificado no navegador. Não coloque a chave privada em chat nem em Git.

6. Limpeza

kubectl delete namespace hpa-teste
rm -f /tmp/hpa.yaml /tmp/ingress.yaml /tmp/nginx-hpa.yaml

Apagar o namespace remove o Deployment, o Service, o HPA, o Ingress e o Secret de uma vez.

Se der erro

Sintoma Causa provável O que fazer
HPA com <unknown>/50% e o evento missing request for cpu O Deployment não tem requests.cpu Preencher a reserva de CPU (passo 2) e esperar o pod ser recriado
Evento failed to get cpu utilization ou metrics not available O metrics-server não está disponível kubectl get apiservice v1beta1.metrics.k8s.io e kubectl -n kube-system get pods | grep metrics
HPA não sobe as réplicas A carga é baixa demais Mais loops, ou reserva de CPU menor
REPLICAS não passa de um valor, e o HPA mostra ScalingLimited Chegou ao maxReplicas ou faltou capacidade no nó kubectl describe hpa; ajustar o máximo
Pod em ImagePullBackOff O nó não baixa a imagem Guia do Quay (registries.yaml)
Ingress: 404 page not found do Traefik Nenhuma regra casou: o Host enviado difere do Ingress Conferir o Host do curl e o host do Ingress
Ingress: 503 ou 502 O Service ou a porta do backend está errado, ou o pod não está pronto kubectl get endpoints -n hpa-teste (deve listar o IP do pod)
nslookup não resolve O registro DNS não existe Pedir ao admin de DNS; usar o Host ou o arquivo hosts
Sem resposta em <IP_NODE_K3S>:80 Firewall, ou o Traefik não está no ar kubectl -n kube-system get svc traefik; liberar a porta
Navegador avisa de certificado O Traefik usa o certificado padrão Passo 5.4
kubectl get ingressclass vazio O cluster não tem controlador de Ingress Habilitar o Traefik do k3s ou instalar um controlador pelo Rancher (Apps); o ingressClassName do Ingress precisa ser o nome dele

Evidências para o relatório

  • Saída de kubectl get hpa -n hpa-teste antes, durante e depois da carga.
  • A seção de eventos de kubectl describe hpa nginx-hpa -n hpa-teste.
  • kubectl get pods -n hpa-teste com várias réplicas.
  • O curl ao <HOST_APLICACAO> com HTTP 200.

Se esse mesmo Deployment for levado depois para o Argo ou o Fleet, retire o campo spec.replicas do Deployment no Git (ou configure o Argo para ignorá-lo). Caso contrário, a sincronização devolve o número de réplicas ao valor do Git e briga com o HPA.

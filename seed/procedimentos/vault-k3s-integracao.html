Como funciona

  1. O pod do k3s apresenta ao Vault o token do ServiceAccount dele e o nome de um papel (role).
  2. O Vault consulta a API do k3s (a API TokenReview) para confirmar que o token é válido. Para isso ele usa a credencial de revisão (passo 2).
  3. Se o papel aceitar aquele ServiceAccount naquele namespace, o Vault devolve um token do Vault, com as permissões da política ligada ao papel.
  4. Com esse token, o pod lê o segredo no caminho que a política permite.
Por isso o Vault precisa alcançar a API do k3s (https://<IP_NODE_K3S>:6443), além de os pods alcançarem o Vault. Essa é a liberação de rede mais fácil de esquecer.

1. Rede e certificadono nó do k3s

Do k3s até o Vault. Use sempre https: o login envia o token do ServiceAccount e o Vault devolve um token dele, e em HTTP os dois trafegariam em texto. O endereço é https://<HOST_VAULT>. Primeiro, sem a CA. O esperado é o erro de certificado, que confirma o diagnóstico:

curl -sS -o /dev/null -w "HTTP %{http_code}\n" --max-time 10 https://<HOST_VAULT>/v1/sys/health

O erro SSL certificate problem aparece porque o certificado é da CA do ingress do OpenShift. O domínio <DOMINIO_APPS_OPENSHIFT> é o mesmo do Quay, então a CA provavelmente é a mesma. Confirme o emissor:

echo | openssl s_client -connect <HOST_VAULT>:443 2>/dev/null | openssl x509 -noout -issuer

Esperado: issuer=CN = ingress-operator@..., igual ao do Quay. Depois, teste com a CA do Quay:

curl -sS -o /dev/null -w "HTTP %{http_code}\n" --max-time 10 --cacert /etc/rancher/k3s/quay-ca.crt https://<HOST_VAULT>/v1/sys/health

Esperado: qualquer código HTTP prova que a rede e o TLS funcionam. Os mais comuns: 200 (Vault ativo), 429 (réplica em espera), 503 (selado) e 501 (não inicializado). HTTP 000 indica que não houve resposta.

O que apareceO que significaO que fazer
SSL certificate problem, mesmo com --cacertA CA usada não é a que assinou o certificado do Vault (o emissor do openssl é outro)Obter a cadeia do Vault, como no passo 2 do tutorial do Quay, e usar a CA certa
HTTP 000, timeout ou could not resolve hostRede bloqueada, ou DNS não resolve o nomePedir a liberação nó → Vault, ou o ajuste do DNS

Do Vault até o k3s. Como o endereço do Vault é uma Route do OpenShift, ele provavelmente roda no próprio OpenShift, e a conexão dele ao k3s sai de um nó do OpenShift, como a do Argo. Se a liberação feita para o Argo cobre todos os nós, talvez já valha, mas NetworkPolicy e EgressFirewall podem ser por namespace. O teste é feito pelo admin do cliente, a partir do servidor do Vault, ou de um pod no namespace do Vault (o pod de teste de rede do roteiro do Argo, trocando o namespace e o endereço):

curl -sk -o /dev/null -w "HTTP %{http_code}\n" --max-time 10 https://<IP_NODE_K3S>:6443/version

Esperado: HTTP 200, 401 ou 403. HTTP 000 indica bloqueio: peça a liberação do Vault até <IP_NODE_K3S>, porta 6443.

2. Credencial de revisãono nó do k3s

O Vault usa um ServiceAccount do k3s, com permissão só de revisar tokens (system:auth-delegator), para validar os tokens dos pods. Abra o arquivo:

vi /tmp/vault-auth.yaml

Cole este conteúdo e salve:

apiVersion: v1
kind: Namespace
metadata:
  name: vault-auth
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: vault-auth
  namespace: vault-auth
---
apiVersion: v1
kind: Secret
metadata:
  name: vault-auth-token
  namespace: vault-auth
  annotations:
    kubernetes.io/service-account.name: vault-auth
type: kubernetes.io/service-account-token
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: vault-auth-delegator
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:auth-delegator
subjects:
- kind: ServiceAccount
  name: vault-auth
  namespace: vault-auth
kubectl apply -f /tmp/vault-auth.yaml
kubectl auth can-i create tokenreviews.authentication.k8s.io --as=system:serviceaccount:vault-auth:vault-auth

Esperado: quatro linhas created e, no can-i, yes.

Dados para o admin do Vault. São dois, e vão para o passo 3:

cat /var/lib/rancher/k3s/server/tls/server-ca.crt
kubectl -n vault-auth get secret vault-auth-token -o jsonpath='{.data.token}' | base64 -d; echo
  • O primeiro é a CA do k3s. É pública, e pode ser enviada normalmente.
  • O segundo é o token de revisão. Não tire print dessa tela, entregue por canal seguro (por exemplo, um cofre de senhas) e limpe a tela em seguida com clear.
Se o token for exposto, apagar só o Secret não o troca: esse tipo de token é determinístico, e o mesmo texto volta a valer. É preciso recriar o ServiceAccount (kubectl -n vault-auth delete secret vault-auth-token, depois kubectl -n vault-auth delete serviceaccount vault-auth e kubectl apply -f /tmp/vault-auth.yaml) e atualizar o Vault com o token novo.

3. Configuração no Vaultadmin do cliente

Esta parte é feita por quem tem permissão no Vault. Os valores sensíveis vão em arquivos, criados no editor, e não na linha de comando. Na PoC, o caminho mais curto é usar o terminal do próprio pod do Vault (a CLI vault já está lá), como descrito em 3.0.

3.0 Preparar o terminal do pod do Vault

Abra o terminal do pod do Vault. A imagem é Alpine (BusyBox), então o editor é o vi simples: i para inserir, colar o texto, Esc e depois :wq + Enter para salvar. Para sair sem salvar, :q!.

a) Aceitar o certificado local. Dentro do pod, a CLI fala com https://127.0.0.1:8200, e o certificado do Vault não tem esse IP. Sem isto aparece cannot validate certificate for 127.0.0.1 because it doesn't contain any IP SANs. Vale só para este terminal:

export VAULT_SKIP_VERIFY=true
vault status

Esperado: Initialized true e Sealed false.

b) Entrar como admin. O comando pede o token e não mostra o que for digitado. Não tire print dessa tela:

vault login

c) Ver os métodos já existentes. O nome escolhido para o <MOUNT_K3S> não pode repetir um deles (a coluna Path termina em /):

vault auth list

d) Testar se o Vault alcança a API do k3s. É a rede do passo 1, vista do lado que importa. O --no-check-certificate só evita parar na CA, que ainda não está neste pod:

wget -T 5 -O- --no-check-certificate https://<IP_NODE_K3S>:6443/version
  • JSON com gitVersion: a rede está liberada.
  • 401 ou 403: também serve. O k3s respondeu, só não aceita consulta anônima.
  • Demora e termina em timeout ou Connection refused: o Vault não alcança o k3s. Peça a liberação de rede do Vault até <IP_NODE_K3S>:6443 antes de seguir; o resto não funciona sem isso.

O que é o MOUNT_K3S

Um Vault pode ter vários métodos de autenticação, cada um ativado num caminho sob auth/ (o chamado *mount*). O do OpenShift provavelmente está em auth/kubernetes, ou com outro nome, e guarda o endereço, a CA e a credencial do OpenShift. O k3s é outro cluster, então precisa do seu próprio método, ativado num caminho novo. O <MOUNT_K3S> é só o nome desse caminho, escolhido por você e pelo admin. Sugestão: k3s-poc.

Onde o <MOUNT_K3S> aparecePara que
vault auth enable -path=<MOUNT_K3S> kubernetesCria o método novo
auth/<MOUNT_K3S>/config e auth/<MOUNT_K3S>/role/<PAPEL>Configura o método e o papel
/v1/auth/<MOUNT_K3S>/loginA chamada de login que o pod faz
Anotação vault.hashicorp.com/auth-path: auth/<MOUNT_K3S>Diz ao Agent Injector qual método usar

Para ver os métodos que já existem, o admin roda vault auth list. O nome escolhido não pode repetir um deles.

3.1 Os arquivos

CA do k3s. Abra o arquivo e cole a CA que você enviou (de -----BEGIN CERTIFICATE----- até -----END CERTIFICATE-----):

vi /tmp/k3s-ca.crt   # CA pública do k3s

Token de revisão. Abra o arquivo e cole o token em uma linha só, sem espaços:

vi /tmp/reviewer.jwt   # token de revisão (sensível), em uma linha

Política. Abra o arquivo e cole o conteúdo (modelo para KV versão 1, a do Vault do cliente):

vi /tmp/policy-k3s.hcl   # política, nome POLITICA = policy-k3s
path "policy-k3s/secret/*" {   # policy-k3s = KV_MOUNT, secret = CAMINHO
  capabilities = ["read", "list"]
}
Na versão 1 do KV, o caminho da política é o do próprio segredo, sem data/ nem metadata/. O /* no fim cobre qualquer segredo dentro da pasta.

Papel. O papel diz ao Vault: "quem apresentar este ServiceAccount, neste namespace, recebe um token com esta política". Ele aceita o ServiceAccount do teste (passo 4) e o da aplicação real. Estes são os três valores do arquivo:

vi /tmp/teste.json   # segredo de teste, sem dado sensível

3.2 Os comandos

vault auth enable -path=poc-vault kubernetes   # cria o método de autenticação do k3s (MOUNT_K3S = poc-k3s-vault)
vault policy write policy-k3s /tmp/policy-k3s.hcl   # grava a política (POLITICA = policy-k3s)
vault write auth/poc-vault/config kubernetes_host=https://<IP_NODE_K3S>:6443 kubernetes_ca_cert=@/tmp/k3s-ca.crt token_reviewer_jwt=@/tmp/reviewer.jwt   # aponta o método para a API do k3s
vault write auth/poc-vault/role/role-k3s @/tmp/role.json   # cria o papel (PAPEL = role-k3s)
vault kv put -mount=policy-k3s secret/teste @/tmp/teste.json   # segredo de teste em policy-k3s/secret/teste (KV_MOUNT = policy-k3s, CAMINHO = secret)

O engine policy-k3s já existe, então não há comando para criá-lo. Confirme que ele é do tipo kv, versão 1 (vault secrets list -detailed). Se for versão 2, os caminhos mudam e levam data/. O mesmo pode ser feito pela interface web do Vault. Apague os arquivos ao terminar, porque um deles tem o token do k3s, e o ~/.vault-token guarda o login de admin:

rm -f /tmp/reviewer.jwt /tmp/k3s-ca.crt /tmp/policy-k3s.hcl /tmp/role.json /tmp/teste.json
rm -f ~/.vault-token
unset VAULT_SKIP_VERIFY

3.3 Conferir

vault read auth/poc-vault/config   # confere o endereço do k3s e o token de revisão
vault read auth/poc-vault/role/role-k3s   # confere o ServiceAccount, o namespace e a política
vault kv get -mount=policy-k3s secret/teste   # confere o segredo de teste

Esperado: a configuração mostra kubernetes_host igual a https://<IP_NODE_K3S>:6443 e a indicação de que o token de revisão foi definido. O papel mostra os nomes e namespaces aceitos e a política.

Se o cliente não puder liberar o Vault até o k3s: a documentação do Vault descreve o parâmetro pem_keys (chaves públicas do cluster) como alternativa ao kubernetes_ca_cert para um Vault fora do Kubernetes, e diz que nem toda instalação do Kubernetes expõe essas chaves. Eu não confirmei como isso se comporta no k3s sem conexão com o cluster. A decisão e o teste ficam com o admin do Vault.

4. Teste do loginno k3s, num pod

Um pod de teste faz o login com o próprio ServiceAccount e lê o segredo de teste. O script usa só sh e curl (não precisa de jq), então serve qualquer imagem que tenha o curl. Na linha image: do pod, use uma imagem que o nó consiga baixar (por exemplo, da Quay). Para conferir antes: kubectl run chk -n poc-k3s-vault --rm -it --restart=Never --image=<IMAGEM> --command -- sh -c 'which curl'.

4.1 Namespace e ServiceAccount. Abra o arquivo, cole o conteúdo e salve:

vi /tmp/poc-k3s-vault-base.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: poc-k3s-vault
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: poc-k3s-vault
  namespace: poc-k3s-vault
kubectl apply -f /tmp/poc-k3s-vault-base.yaml

4.2 A CA do Vault, para o pod confiar no certificado. A forma mais segura é usar a cadeia que o próprio Vault apresenta, que já traz a raiz (ingress-operator). No nó do k3s:

openssl s_client -connect <HOST_VAULT>:443 -showcerts </dev/null 2>/dev/null | awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/' > /tmp/vault-ca.crt   # cadeia do Vault, com a raiz
openssl crl2pkcs7 -nocrl -certfile /tmp/vault-ca.crt | openssl pkcs7 -print_certs -noout   # o último deve ter subject igual ao issuer (raiz)
curl -sS -o /dev/null -w "HTTP %{http_code}\n" --max-time 10 --cacert /tmp/vault-ca.crt https://<HOST_VAULT>/v1/sys/health   # qualquer código HTTP confirma

Se o último certificado não for uma raiz (subject diferente do issuer) ou o curl der erro de certificado, o servidor não envia a raiz: peça a CA do ingress ao time do OpenShift e cole no arquivo com o vi. A CA do Quay só serve se for a mesma raiz.

kubectl create configmap vault-ca -n poc-k3s-vault --from-file=ca.crt=/tmp/vault-ca.crt

4.3 O pod. Abra o arquivo, cole o conteúdo, troque o nome e a tag da imagem (em vermelho) e salve:

vi /tmp/poc-k3s-vault-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: poc-k3s-vault
  namespace: poc-k3s-vault
spec:
  serviceAccountName: poc-k3s-vault
  restartPolicy: Never
  containers:
  - name: teste
    image: <REGISTRY_QUAY>/<IMAGEM>:<TAG>   # imagem da Quay com sh e curl
    command: ["sh", "-c"]
    args:
    - |
      JWT=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
      RESP=$(curl -sS --max-time 15 --cacert /vault-ca/ca.crt -X POST -d "{\"jwt\":\"$JWT\",\"role\":\"role-k3s\"}" https://<HOST_VAULT>/v1/auth/poc-vault/login)   # papel role-k3s, método poc-vault
      echo "== login (sem o token) =="
      echo "$RESP" | sed 's/"client_token":"[^"]*"/"client_token":"***"/'   # esconde o token do Vault

4.4 Evidência da PoC e diagnóstico do 403 na leitura

No teste feito, o login funcionou, e a leitura do segredo devolveu HTTP 403. O login devolveu estes dados, e cada um prova um item da configuração:

O que o login devolveuO que isso prova

Com isso, tudo que depende do nome do método, do papel, do ServiceAccount e do namespace está compatível. O 403 está só na política contra o caminho lido: o Vault confere a política antes de ver se o segredo existe. Um segredo inexistente com política certa dá 404, e nunca 403. Logo, o caminho pedido (/v1/policy-k3s/secret/teste) não casa com nenhuma regra da policy-k3s.

5. Como a aplicação consome o Vaultdecisão

O passo 4 prova o login e a leitura. Falta definir como a aplicação real obtém os segredos. A planilha da PoC cita o Vault como dependência de inicialização do email-corporativo-processar. Confirme com o time dele qual dos mecanismos o OpenShift usa hoje, o que costuma aparecer nas anotações do pod.

MecanismoO que exige no k3sObservação
Vault Agent Injector (anotações vault.hashicorp.com/... no pod)Instalar o injetor no k3s, apontando para o Vault externoÉ o mais comum em manifests vindos do OpenShift
CSI ProviderInstalar o Secrets Store CSI Driver e o provedor do VaultOs segredos viram arquivos montados no pod
Vault Secrets OperatorInstalar o operador e criar os recursos de conexão e de autenticaçãoSincroniza o segredo do Vault para um Secret do Kubernetes
Leitura direta pela aplicação (API ou SDK)Nada, além do papel e da políticaA aplicação faz o login, como o pod de teste

Se for o Agent Injector, estas anotações no pod mudam em relação ao OpenShift, porque o método de autenticação e o papel são os novos:

vault.hashicorp.com/agent-inject: "true"
vault.hashicorp.com/role: "role-k3s"
vault.hashicorp.com/auth-path: "auth/poc-vault"
vault.hashicorp.com/agent-inject-secret-config.txt: "policy-k3s/secret/teste"
  • O endereço do Vault e a CA ficam na configuração do injetor, ou em anotações do pod. Os nomes exatos dos valores do Helm chart e das anotações de CA dependem da versão: confirme na documentação da versão instalada.
  • Os manifests migrados do OpenShift costumam trazer o caminho de autenticação, o papel e o endereço antigos: troque todos.
  • Eu monto o passo a passo de instalação do mecanismo escolhido quando você souber qual a aplicação usa.

6. Limpeza e revogaçãoos dois lados

No k3s:

kubectl delete namespace poc-k3s-vault
kubectl delete clusterrolebinding vault-auth-delegator
kubectl delete namespace vault-auth
rm -f /tmp/vault-auth.yaml /tmp/poc-k3s-vault-base.yaml /tmp/poc-k3s-vault-pod.yaml /tmp/vault-ca.crt

No Vault (admin do cliente), ao fim da PoC:

vault auth disable poc-k3s-vault
vault policy delete policy-k3s
vault kv delete -mount=policy-k3s secret/teste

Se o token de revisão foi exposto, recrie o ServiceAccount (nota do passo 2) e reaplique o comando vault write auth/poc-vault/config ... completo do passo 3.2, com o token novo. A escrita nesse caminho substitui a configuração inteira.

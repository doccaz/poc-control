Argo CD do cliente → k3s: roteiro da sessão

Objetivo: cadastrar o k3s (poc-downstream, <IP_NODE_K3S>) no Argo CD do cliente, que atende os clusters OpenShift, para entregar aplicações nele.

Fluxo: 1 Rede → 2 Certificado → 3 Credencial → 4 Cluster no Argo → 5 Conferir → 6 Application → 7 Teste GitOps.

Convenções deste roteiro:

  • Tudo que cria ou altera arquivo usa o editor (vi): você abre o arquivo e cola o conteúdo. Não há cluster add, repo add nem app set com parâmetros. O cadastro do cluster é declarativo (um Secret), e você controla tudo no arquivo.
  • Comandos do k3s são rodados no nó como root (ou com sudo).
  • Onde aparece <...>, troque pelo valor real. No vi, para trocar todas as ocorrências de uma vez: :%s/<APPPROJECT>/valor/g (ajuste o valor).

1. Rede — no OpenShift do cliente

Prova que o tráfego do Argo chega na API do k3s. Precisa de oc no OpenShift do cliente; sem acesso, o admin roda e envia a saída.

Abra o arquivo:

vi /tmp/net-test.yaml

Cole este conteúdo (troque o namespace) e salve:

apiVersion: v1
kind: Pod
metadata:
  name: net-test
  namespace: argo-cd
spec:
  restartPolicy: Never
  containers:
  - name: net-test
    image: nicolaka/netshoot
    command: ["sh", "-c"]
    args:
    - |
      nc -zv -w 5 <IP_NODE_K3S> 6443
      curl -sk --max-time 8 -o /dev/null -w "HTTP %{http_code}\n" https://<IP_NODE_K3S>:6443/version

Execute, espere alguns segundos e leia o resultado:

oc apply -f /tmp/net-test.yaml
oc logs net-test -n argo-cd
oc delete pod net-test -n argo-cd

Esperado: o nc mostra open, succeeded ou Connected, e o curl mostra HTTP 200, 401 ou 403.

Se o pod não subir (imagem do Docker Hub bloqueada ou política de segurança), teste a partir de um nó: oc get nodes, depois oc debug node/<nome-do-no> e, dentro do shell, os mesmos dois comandos.

2. Certificado — no nó do k3s

echo | openssl s_client -connect <IP_NODE_K3S>:6443 2>/dev/null | openssl x509 -noout -checkip <IP_NODE_K3S>

Esperado: IP <IP_NODE_K3S> does match certificate. Se for isso, pule para o passo 3.

Se aparecer does NOT match certificate, o IP não consta no certificado. Crie um arquivo complementar:

mkdir -p /etc/rancher/k3s/config.yaml.d
vi /etc/rancher/k3s/config.yaml.d/10-tls-san.yaml

Conteúdo (o + acrescenta à lista que o config.yaml já tiver):

tls-san+:
  - <IP_NODE_K3S>

Antes de reiniciar, confira a porta de que a sua imagem depende (o registro local da 6545), reinicie e repita o teste acima:

(echo > /dev/tcp/127.0.0.1/6545) && echo "6545 ok"
systemctl restart k3s
kubectl get nodes

3. Credencial — no nó do k3s

Abra o arquivo:

vi /tmp/argocd-manager.yaml

Cole este conteúdo e salve:

apiVersion: v1
kind: ServiceAccount
metadata:
  name: argocd-manager
  namespace: kube-system
---
apiVersion: v1
kind: Secret
metadata:
  name: argocd-manager-token
  namespace: kube-system
  annotations:
    kubernetes.io/service-account.name: argocd-manager
type: kubernetes.io/service-account-token
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: argocd-manager
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: ServiceAccount
  name: argocd-manager
  namespace: kube-system

Aplique:

kubectl apply -f /tmp/argocd-manager.yaml

Teste: o token e a CA funcionam? Este comando usa o token sem exibi-lo:

curl -s --cacert /var/lib/rancher/k3s/server/tls/server-ca.crt -H "Authorization: Bearer $(kubectl -n kube-system get secret argocd-manager-token -o jsonpath='{.data.token}' | base64 -d)" https://<IP_NODE_K3S>:6443/api/v1/namespaces | head -c 200

Esperado: um JSON que começa com "kind": "NamespaceList". Se der 401, espere uns segundos e repita (o token leva um instante para ser gerado); se persistir, o token está errado.

Agora leia os dois valores que irão no Secret do passo 4. Não tire print desta tela.

kubectl -n kube-system get secret argocd-manager-token -o jsonpath='{.data.token}' | base64 -d; echo
base64 -w0 /var/lib/rancher/k3s/server/tls/server-ca.crt; echo

O primeiro é o token; o segundo é a CA em base64, em uma linha só. Copie cada um (selecionando o texto com o mouse) para o passo 4 e, em seguida, limpe a tela:

clear

Se o token foi exposto (print, chat, e-mail), revogue e gere outro. Nada depende dele antes do passo 4, então o custo é baixo. Apagar o Secret invalida o token, e o apply o recria:

kubectl -n kube-system delete secret argocd-manager-token
kubectl apply -f /tmp/argocd-manager.yaml

Espere uns segundos, repita o teste do token acima e leia o valor novo.

4. Cluster no Argo — no OpenShift do cliente

Antes de cadastrar, olhe o que já existe no Argo (ponto de atenção do início):

oc get appproject -n argo-cd
oc get appproject -n argo-cd -o yaml | grep -n -A4 "destinations"
oc get applicationset -A

Procure: destinations com server: '*' e ApplicationSets com clusters: sem seletor. Se existirem, combine com o admin como restringir (por exemplo, com project: abaixo) antes de seguir.

Crie o arquivo com permissão restrita e abra-o:

umask 077
vi /tmp/cluster-k3s-poc.yaml

Cole este conteúdo, troque os três <...> (token e CA do passo 3) e salve:

apiVersion: v1
kind: Secret
metadata:
  name: cluster-k3s-poc
  namespace: argo-cd
  labels:
    argocd.argoproj.io/secret-type: cluster
type: Opaque
stringData:
  name: k3s-poc
  server: https://<IP_NODE_K3S>:6443
  config: |
    {
      "bearerToken": "<TOKEN>",
      "tlsClientConfig": { "insecure": false, "caData": "<CA_EM_BASE64>" }
    }

Para restringir o cluster a um único projeto do Argo, acrescente esta linha em stringData:, no mesmo nível de name: (o Argo só deixa as Applications desse projeto usarem o cluster):

  project: <APPPROJECT>

Aplique e apague os arquivos (contêm o token):

oc apply -f /tmp/cluster-k3s-poc.yaml
rm -f /tmp/cluster-k3s-poc.yaml /tmp/argocd-manager.yaml

Se quem aplica é o admin do Argo, entregue o arquivo a ele por canal seguro.

5. Conferir — na UI do Argo

Settings → Clusters → k3s-poc: o esperado é Connection Successful.

Se aparecer Unknown, aguarde 1 a 2 minutos: o Argo só testa a conexão quando algo usa o cluster. Prossiga para o passo 6, que a prova de fato. Se aparecer Failed, leia a mensagem e use a tabela do final.

6. Application — no OpenShift do cliente e na UI do Argo

6.1 Repositório. Com o repositório público (fleet-examples), não há nada a fazer. Para um repositório privado do cliente, crie um Secret de repositório:

umask 077
vi /tmp/repo-poc.yaml

apiVersion: v1
kind: Secret
metadata:
  name: repo-poc
  namespace: argo-cd
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  type: git
  url: <URL_DO_REPOSITORIO>
  username: <USUARIO>
  password: <TOKEN_DO_GIT>

oc apply -f /tmp/repo-poc.yaml
rm -f /tmp/repo-poc.yaml

6.2 Application, com sincronização manual. Abra o arquivo:

vi /tmp/application.yaml

Cole este conteúdo e salve (troque o namespace e o projeto):

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook-k3s
  namespace: argo-cd
spec:
  project: <APPPROJECT>
  source:
    repoURL: https://github.com/rancher/fleet-examples
    targetRevision: master
    path: simple
  destination:
    name: k3s-poc
    namespace: argo-poc
  syncPolicy:
    syncOptions:
    - CreateNamespace=true

oc apply -f /tmp/application.yaml

Na UI do Argo, abra a aplicação guestbook-k3s. Clique em Sync, marque Dry Run e confirme: ele valida que o Argo renderiza os manifests e que o destino é permitido, sem alterar nada. Depois faça o Sync de verdade.

Esperado: Synced e Healthy. Confira também no k3s:

oc get application guestbook-k3s -n argo-cd
kubectl get pods,svc -n argo-poc

6.3 Sincronização automática. Reabra o arquivo, acrescente automated ao syncPolicy e reaplique:

vi /tmp/application.yaml

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=true

oc apply -f /tmp/application.yaml

7. Teste GitOps: atualização e rollback

Num fork do repositório, troque a imagem do Deployment por uma do Quay interno, que prova também a integração com o Quay: <REGISTRY_QUAY>/<repositorio>:<tag>. Faça commit e push.

Aguarde o Argo sincronizar (até 3 minutos, ou use Refresh na UI) e confira no k3s:

kubectl get deploy -n argo-poc -o jsonpath='{.items[*].spec.template.spec.containers[*].image}'; echo

Esperado: a imagem nova. Para o rollback, faça git revert do commit, push, e repita a conferência: a imagem anterior deve voltar.

8. Limpeza ao fim da PoC

No OpenShift do cliente:

oc delete application guestbook-k3s -n argo-cd
oc delete secret cluster-k3s-poc -n argo-cd

No k3s (revoga a credencial):

kubectl delete clusterrolebinding argocd-manager
kubectl -n kube-system delete secret argocd-manager-token
kubectl -n kube-system delete serviceaccount argocd-manager

Se der erro

Sintoma Causa provável O que fazer
Passo 1: nc sem resposta, curl com 000 Tráfego bloqueado (firewall, NetworkPolicy, EgressFirewall, proxy) Pedir a liberação Argo → <IP_NODE_K3S>:6443
Passo 1: Connection refused Chegou no k3s, mas nada escuta No k3s: ss -ltnp | grep 6443
Passo 2: does NOT match certificate O IP não está no certificado tls-san do passo 2 e reiniciar
Passo 3: 401 ao testar o token Token ainda não gerado, ou errado Esperar e repetir; conferir o ClusterRoleBinding
Cluster Failed: x509: certificate signed by unknown authority caData errada, ou cortada na colagem Refazer o base64 -w0 e colar em uma linha
Cluster Failed: x509: certificate is valid for ..., not <IP_NODE_K3S> IP fora do certificado Passo 2
Cluster Failed: Unauthorized Token errado ou com espaço sobrando Refazer a leitura do token
Cluster Failed: timeout / connection refused Rede Passo 1
destination ... is not permitted in project O AppProject não lista o k3s destinations do projeto (ou o project: do Secret não bate)
ComparisonError / repositório inacessível Argo sem acesso ao Git, ou path errado Passo 6.1 e conferir a pasta
Pods em ImagePullBackOff no k3s O nó não baixa a imagem Guia do Quay (registries.yaml)
O Secret do cluster sumiu Alguém ou algum GitOps o reverteu Perguntar ao admin (ponto de atenção)
